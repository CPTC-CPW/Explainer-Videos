Aggregates squash many rows into one

An aggregate function reads a whole column of values and hands back a single value: how many, the total, the average, the smallest, the largest.

Put aggregates in the SELECT list with no GROUP BY and the result is exactly one row, whether 10 rows went in or 10 million.

To keep every row on screen, this explainer mostly works with the 10 invoices from three vendors in the AP database: IBM (34), Blue Cross (37) and Malloy Lithographing (110).

Key idea: without GROUP BY, all the rows that survive WHERE form one big group, and each aggregate boils that group down to one value.
FROM›WHERE›GROUP BY›HAVING›SELECT›ORDER BY 
SELECT COUNT(*)          AS InvoiceCount,
       SUM(InvoiceTotal) AS InvoiceSum,
       AVG(InvoiceTotal) AS InvoiceAvg,
       MIN(InvoiceTotal) AS Smallest,
       MAX(InvoiceTotal) AS Largest
FROM Invoices
WHERE VendorID IN (34, 37, 110);

Always name the result. An aggregate has no column name of its own, so SSMS shows (No column name). Add AS InvoiceSum to every one.
Aggregate an expression, not just a columnSUM(InvoiceTotal - PaymentTotal - CreditTotal) adds up the balance due on every invoice. SQL works out the expression row by row, then adds the results.

COUNT(*) counts rows. COUNT(column) counts values.

COUNT(*) counts every row, full stop. COUNT(PaymentDate) counts only the rows where PaymentDate is not NULL. Three of our ten invoices haven't been paid, so their PaymentDate is NULL and they're skipped.

COUNT(DISTINCT VendorID) counts different values: ten invoices, but only three vendors.

Key idea: every aggregate except COUNT(*) ignores NULLs. That's usually what you want, but it can quietly change an average (more on that in Gotchas).

       COUNT(DISTINCT VendorID) AS Vendors
FROM Invoices
WHERE VendorID IN (34, 37, 110);

GROUP BY sorts rows into buckets

One row for the whole table is useful, but usually the question is "per something": invoices per vendor, sales per month, vendors per state.

GROUP BY VendorID makes one bucket for each different VendorID and drops every row into its bucket. Our ten invoices have three different vendors, so we get three buckets. Every row lands in exactly one.

Key idea: the column after GROUP BY decides what a bucket is. Change it and you change the question.
FROM›WHERE›GROUP BY›HAVING›SELECT›ORDER BY 
SELECT VendorID, COUNT(*) AS InvoiceCount,
       SUM(InvoiceTotal) AS InvoiceSum
FROM Invoices
WHERE VendorID IN (34, 37, 110)
GROUP BY VendorID;

Each bucket becomes one row

Now the aggregates run once per bucket instead of once for the whole table. Each bucket collapses into a single result row: its VendorID, plus the count, sum and average of just the invoices inside it.

Three buckets in, three rows out. Check the sums against the last step: IBM's two invoices, 116.54 + 1083.58, make 1200.12.

Order isn't guaranteed. SQL Server returns groups in whatever order is convenient. If the order matters, add ORDER BY, e.g. ORDER BY InvoiceSum DESC.

The rule: grouped, or aggregated

Try to show each vendor's InvoiceNumber next to its count and SQL Server refuses. Look at Malloy's bucket: it holds five different invoice numbers, but the bucket only gets one row. Which number should go in it? SQL won't guess.

So every column in the SELECT list must be one of two things:

  • In the GROUP BY, so it has one value per bucket by definition (like VendorID), or
  • Inside an aggregate, which turns many values into one (like COUNT(*) or MAX(InvoiceNumber)).
Fixing it: usually just remove the column. Adding InvoiceNumber to the GROUP BY also "works", but then every invoice is its own bucket, and you're no longer summarizing anything.
SELECT VendorID, InvoiceNumber,
       COUNT(*) AS InvoiceCount
FROM Invoices
GROUP BY VendorID;

You write SELECT first. SQL runs it fifth.

The clauses are written in one order but processed in another. Once you know the processing order, most summary-query rules stop being things to memorize: each clause can only use what the clauses before it have already made.

1 · FROMPick the table(s) and join them
2 · WHEREFilter rows, one at a time
3 · GROUP BYSort the surviving rows into buckets
4 · HAVINGFilter whole buckets
5 · SELECTWork out the output columns and aliases
6 · ORDER BYSort the final rows
So an aggregate can't go in WHERE

WHERE runs at step 2, before any buckets exist, so there's nothing to SUM yet:

SELECT VendorID, COUNT(*) AS InvoiceCount
FROM Invoices
WHERE SUM(InvoiceTotal) > 1000
GROUP BY VendorID;
Msg 147, Level 15, State 1, Line 1
An aggregate may not appear in the WHERE clause unless it is in a subquery contained in a HAVING clause or a select list, and the column being aggregated is an outer reference.
…but ORDER BY can use anything

ORDER BY runs last, after SELECT has named its columns, so it can sort by an aggregate or by its alias:

SELECT VendorID, SUM(InvoiceTotal) AS InvoiceSum
FROM Invoices
WHERE VendorID IN (34, 37, 110)
GROUP BY VendorID
ORDER BY InvoiceSum DESC;

The fix for the error on the left is the next step: HAVING, which runs after the buckets exist.

HAVING throws out whole buckets

HAVING is a WHERE for groups. It runs after GROUP BY, so its condition can use aggregates, and it keeps or drops an entire bucket at a time.

Which vendors have invoices totalling more than $1,000? Blue Cross's bucket only adds up to 564.00, so the whole bucket goes, and Blue Cross never reaches the result.

Key idea: a condition with an aggregate in it (SUM, COUNT, AVG…) belongs in HAVING.
FROM›WHERE›GROUP BY›HAVING›SELECT›ORDER BY 
SELECT VendorID, COUNT(*) AS InvoiceCount,
       SUM(InvoiceTotal) AS InvoiceSum
FROM Invoices
WHERE VendorID IN (34, 37, 110)
GROUP BY VendorID
HAVING SUM(InvoiceTotal) > 1000;

Swap HAVING SUM(InvoiceTotal) > 1000 for WHERE InvoiceTotal > 1000 and you're asking a different question. WHERE throws out individual invoices before grouping; HAVING throws out whole vendors after.

Rule of thumb: about individual rows → WHERE. About a group's total, count or average → HAVING. A query can use both. Filtering rows in WHERE first also means less to group.

Join first, then summarize

Invoices only store a VendorID. To group by a vendor's name, join Vendors in. The join happens in FROM, the first step, so by the time GROUP BY runs, every invoice row already carries its vendor's name.

This query answers a real accounts-payable question: who do we still owe, and how much? WHERE keeps only invoices with a balance due, GROUP BY makes one bucket per vendor, and ORDER BY puts the biggest debt on top.

Tip: group by v.VendorID, v.VendorName, not just the name. Two different vendors could share a name, and grouping by the ID keeps them apart. (Here the result is the same.)
SELECT v.VendorName,
       COUNT(*) AS UnpaidInvoices,
       SUM(i.InvoiceTotal - i.PaymentTotal
           - i.CreditTotal) AS BalanceDue
FROM Vendors v
    JOIN Invoices i ON i.VendorID = v.VendorID
WHERE i.InvoiceTotal - i.PaymentTotal
      - i.CreditTotal > 0
GROUP BY v.VendorName
ORDER BY BalanceDue DESC;

Join one row too many and totals multiply

Wells Fargo Bank has one invoice, #12, for 662.00. That invoice has four line items in InvoiceLineItems.

Join all three tables and that one invoice turns into four rows, each carrying the same 662.00 InvoiceTotal. Now COUNT(*) says 4 invoices and SUM(InvoiceTotal) says 2648.00, four times the truth. No error, just a wrong answer.

Check: after a join, ask "what is one row now?" Here it's one line item, not one invoice. Count with COUNT(DISTINCT i.InvoiceID) and add up the line-item amounts, or leave out the join you don't need.

AVG skips NULLs. It doesn't count them as zero.

How many days do we take to pay? DATEDIFF(day, InvoiceDate, PaymentDate) works it out per invoice. For the three unpaid invoices PaymentDate is NULL, so the difference is NULL too.

AVG leaves those three out: 185 days ÷ 7 paid invoices. Divide by COUNT(*) instead and the unpaid ones count as zero days: 185 ÷ 10. Neither is wrong; they answer different questions. Decide which one you mean.

Second gotcha: DATEDIFF returns a whole number, so AVG returns a whole number too. 185 ÷ 7 is really 26.43, but SQL Server shows 26. Use AVG(DATEDIFF(…) * 1.0) to keep the decimals: 26.428571.
SELECT AVG(DATEDIFF(day, InvoiceDate, PaymentDate))
           AS AvgDaysToPay,
       SUM(DATEDIFF(day, InvoiceDate, PaymentDate))
           / COUNT(*) AS DaysPerInvoice
FROM Invoices
WHERE VendorID IN (34, 37, 110);

Bonus: a grand total row with ROLLUP

Reports often want a total under the per-group rows. Wrap the GROUP BY column in ROLLUP(…) and SQL Server adds one extra row that summarizes every bucket together.

That extra row has NULL in the VendorID column, because it doesn't belong to any one vendor. Its numbers match the one-row query from the start of this explainer: 10 invoices, 121656.53.

Optional extra. With two grouping columns, ROLLUP(VendorState, VendorCity) gives a subtotal per state as well as a grand total.
SELECT VendorID, COUNT(*) AS InvoiceCount,
       SUM(InvoiceTotal) AS InvoiceSum
FROM Invoices
WHERE VendorID IN (34, 37, 110)
GROUP BY ROLLUP(VendorID);

Cheat sheet

Everything on one screen. If you remember one sentence: GROUP BY makes buckets, aggregates squash each bucket to one row, and HAVING filters the buckets.

Processing order
FROM›WHERE›GROUP BY›HAVING›SELECT›ORDER BY
01 · Aggregates
  • COUNT, SUM, AVG, MIN, MAX
  • No GROUP BY → exactly one row
  • Name every result with AS
02 · NULLs
  • COUNT(*) counts rows
  • Every other aggregate skips NULLs
  • COUNT(DISTINCT col) counts different values
03 · GROUP BY
  • One bucket per different value (or combination)
  • One result row per bucket
  • SELECT columns: grouped or aggregated
04 · WHERE vs HAVING
  • WHERE filters rows, before grouping
  • HAVING filters buckets, after
  • Aggregate in the condition → HAVING
05 · Gotchas
  • Add ORDER BY if order matters
  • After a join, ask "what is one row now?"
  • AVG of whole numbers → whole number
