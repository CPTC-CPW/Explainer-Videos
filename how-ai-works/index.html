An LLM is a next-token predictor

Strip away the hype and a large language model does one thing: given a sequence of tokens, it outputs a probability for every possible next token. The app picks one, appends it, and runs the model again.

Chat, code generation, agents — all of it is built on this loop. Think of the model as a function: probs = model(tokens_so_far), with billions of learned numbers (weights) inside. It doesn't look anything up and it doesn't run your code. It's math over the input.

Key idea: the model writes one token per pass. A 500-token answer is 500 passes through the model, each one re-reading everything before it.

Models read tokens, not words

Before the model sees anything, a tokenizer splits text into chunks from a fixed vocabulary — common words, word pieces, punctuation, whitespace runs. Each token becomes an integer ID, and that sequence of integers is the model's real input.

Tokens are also the unit of everything that matters to your budget: price, rate limits, speed and the size of the context window are all counted in tokens.

This is why models have famously miscounted the r's in “strawberry” — often answering two when there are three. The model never sees ten letters, just a few chunks like str aw berry, so spelling and letter-counting questions are surprisingly hard for it.

Rule of thumb: about 4 characters of English ≈ 1 token, so 100 tokens ≈ 75 words. Code, long identifiers, deep indentation and non-English text usually cost more tokens per character. Exact splits depend on the model.

Vectors, then attention

Each token ID is swapped for an embedding: a long vector of numbers (thousands of dimensions) learned during training, where similar meanings land near each other.

Those vectors flow through a stack of transformer layers. In each layer, attention lets every token look back at every earlier token and pull in information from the ones that matter. That's how “it” knows it means “the server”.

Why you care: the model can only attend to what's in its input. If the relevant file, error or decision isn't in the context, the model can't use it — and burying it under noise makes it harder to find.

Picking the next token

The last layer scores every token in the vocabulary, and those scores become a probability distribution. The app then samples one token from it.

Temperature controls how adventurous that pick is. Near 0, the top token wins almost every time — more repeatable, good for code and extraction. Higher values flatten the odds — more variety, more surprises, more mistakes.

Consequence: the model is optimised to be plausible, not verified. A confident-sounding API that doesn't exist is just a high-probability sequence. Always run and test what it writes.

No memory — just a context window

The model keeps nothing between calls. A chat only seems to remember because the app re-sends the whole conversation every turn: system prompt, every message, every file and tool result so far.

All of it has to fit in the context window, a hard limit counted in tokens. When it fills up, older material must be dropped or summarised — and answers often get worse well before the limit, as the details that matter get buried.

It also means big context is expensive context. Paste a whole file, a long log or a large data dump and you don't pay for it once — it's re-sent as input on every turn after that. A single 2,000-line log can easily be tens of thousands of tokens, multiplied by every message that follows.

Key idea: every turn is a brand-new request carrying everything before it. That single fact explains most of the token advice in the next chapter.

What you actually pay for

Every request is billed as input tokens (everything sent) plus output tokens (everything generated). Output tokens usually cost several times more per token than input, and they are produced one pass at a time — so long answers are expensive and slow.

In a coding assistant, the part you typed is often the smallest slice. Instructions, tool definitions, conversation history and file contents ride along on every request.

Check your tool: most assistants can show token usage or context fill (in Claude Code, /context and /cost). Look before you guess.

Long chats compound

Because history is re-sent, turn 30 of a conversation pays again for turns 1 to 29. The cost of each turn grows with the chat, so the total cost grows much faster than the number of turns.

Long, wandering sessions are also worse at the work: stale plans, abandoned approaches and old file versions compete for the model's attention with what's true now.

Habit: one task, one session. When you switch tasks, clear or start fresh (in Claude Code, /clear). If you must continue, summarise first (/compact).

Point, don't paste

The cheapest token is the one you never send. A precise request costs less and gets a better answer, because the model isn't hunting for the signal in a pile of noise.

Eight habits for a limited budget

None of these make you slower. Most of them make the answers better too.

01One task, one sessionClear or start fresh when you switch tasks. Old context is paid for on every turn.
02Point, don't pasteGive file paths, function names and line numbers. Paste only the log lines that matter.
03Ask for diffs, not filesOutput is the expensive side. “Only the changed lines” and “be brief” both save real money.
04Compact long sessionsWhen you must continue, summarise the state into a short note and carry on from that.
05Right-size the modelSmall, fast models for renames, boilerplate and search. Large models for design and hard bugs.
06Keep always-on context leanShort CLAUDE.md / rules files. Disconnect MCP servers you aren't using in this project.
07Let caching workPrompt caching discounts a repeated prefix. Keep stable content (instructions, docs) first and unchanged.
08Stop runaway loopsIf an agent keeps retrying the same failing fix, interrupt, add the missing fact, re-scope.

Tool use: how a text model gets hands

A model can only produce text. Tool use works by describing tools to it — a name, a description and a JSON schema for the inputs. The model can then reply with a structured tool call instead of prose.

Your application (the host) runs the call, then sends the result back as part of the next request. The model never executes anything itself; the host decides what actually happens.

Budget note: tool definitions are part of the input on every request, and every tool result lands in the context. More tools and bigger results mean more tokens.

MCP: one standard plug for tools

The Model Context Protocol is an open standard for connecting AI apps to outside systems. Instead of every app writing a custom integration for every service, a service ships one MCP server and any MCP-capable host can use it — like USB for AI tools.

A server can expose three kinds of things:

  • Tools — actions the model can call: create_issue, query
  • Resources — data the app can read into context: files, schemas, records
  • Prompts — reusable templates the server offers to the user

Servers run locally as a subprocess (stdio) or remotely over HTTP. The host's MCP client speaks JSON-RPC to each one.

MCP in practice

Reach for MCP when the model needs live data or actions in another system. If a command-line tool already does the job (git, gh, psql), the agent can often just run it — no server needed.

Common use cases
  • Issue tracker — read the ticket, implement it, link the PR and update the status
  • Database, read-only — inspect the schema and sample rows so generated queries actually match
  • Browser automation — open your app, click through the flow, screenshot to verify a UI fix
  • Current docs — fetch today's library docs instead of relying on what the model learned in training
  • Observability — pull the real stack trace from your error tracker into the debugging session
Best practices
  • Enable per project, not globally. Each connected server's tool definitions take context on every request.
  • Least privilege. Read-only DB users, narrowly scoped tokens, never production writes from a dev session.
  • Install only servers you trust. A local server runs code on your machine and sees what you send it.
  • Treat tool output as untrusted. Web pages, tickets and emails can contain prompt-injection text.
  • Keep results small. Filter, paginate and select columns instead of dumping whole tables.
  • Secrets stay in config. Use environment variables or the host's secret store — never paste keys into prompts.

An agent is a model in a loop

Agent = model + tools + a goal, running in a loop. It plans a step, calls a tool, reads the result, and decides what's next — until the goal is met or it needs you. A coding assistant that edits files and runs your tests is an agent.

There's no new magic here: it's the tool-use round trip from before, repeated, with the model choosing the next tool each time.

Budget note: every lap is another model call that re-reads the whole growing context. Clear goals and a way to check success (tests, a build, a linter) end the loop sooner.

Custom agents vs subagents

Both start as the same thing: a markdown file holding a description, the tools it may use, optionally a model, and its instructions. What differs is who invokes it — and whose context it uses.

  • Custom agent — you pick it from the agent picker and it takes over your chat. It works inside your conversation, so everything it reads fills your context window.
  • Subagent — another agent hands it a task. It runs in its own fresh context and sends back only a summary.
# .github/agents/reviewer.agent.md  (Copilot · VS Code)
---
description: Reviews changes for bugs, security
  and missing tests.
tools: ['search', 'usages']
user-invocable: true            # show in picker
disable-model-invocation: false # allow as subagent
---
You are a senior reviewer. Reply with at most
5 findings, most severe first, with file:line.
# .claude/agents/code-reviewer.md  (Claude Code)
---
name: code-reviewer
description: Reviews a diff for bugs, security and
  missing tests. Use after any code change.
tools: Read, Grep, Glob
---
You are a senior reviewer. …

In VS Code, one .agent.md file can work both ways; the two flags above control which. Claude Code's agent files are used mainly as subagents. Field and tool names vary by tool and version — Visual Studio's Copilot may differ, so check its docs.

Custom agents & subagents in practice

Switch to a custom agent when you want a different way of working. Delegate to a subagent when a job is self-contained, noisy, or parallel — and you only need its conclusion, not every file it read on the way.

Common use cases
  • Planner (custom agent) — a read-only mode you switch to for designing an approach before any code is written
  • Code reviewer — read-only, runs after changes, reports the top findings
  • Test runner — runs the suite, reports only the failures and likely causes
  • Codebase explorer — “where is auth handled?” → a short list of files and functions
  • Docs & changelog writer — turns a diff into release notes in your house style
  • Parallel investigations — several independent questions answered at once
Best practices
  • Pick the right mode. A custom agent changes how you work; a subagent keeps noisy work out of your context.
  • One job per agent. Its description is how the main agent decides when to delegate — make it specific.
  • Fewest tools that work. A reviewer doesn't need write access; a researcher doesn't need a shell.
  • Ask for short, structured returns. “Max 5 findings, file:line each” keeps the summary from flooding your context.
  • Match model to task. A smaller model is often enough for search and summarising.
  • Don't over-delegate. Starting an agent has overhead; a two-line edit is cheaper done inline.
  • Verify the result. Agents can be confidently wrong — read the diff and rerun the tests.
  • Commit agent files to the repo so the whole team shares and improves them.

Skills: know-how loaded on demand

A skill is a folder holding a SKILL.md file of instructions, plus optional scripts and reference files. It teaches the model one specific procedure — your release checklist, how your team writes migrations, your report format.

The trick is progressive disclosure. Up front, only each skill's name and one-line description sit in context. When a task matches, the model reads the full SKILL.md. Extra files are opened only if that step needs them. You can install many skills and pay for few.

Skills in practice

Write a skill when you notice yourself explaining the same procedure to the AI twice. Write it once, and the model picks it up whenever the task comes around.

Common use cases
  • Team conventions — commit messages, PR descriptions, branch naming
  • Scaffolding — a new endpoint, component or service that follows the house pattern
  • Checklists — release steps, security review, accessibility audit
  • Documents & data — your report format, spreadsheet layouts, API docs style
  • Repetitive transforms — migrating calls to a new API version across a codebase
Best practices
  • Write the description as a trigger. Say what it does and when to use it — it's all the model sees up front.
  • Keep SKILL.md focused. Move long references into separate files it links to, so they load only when needed.
  • Script the deterministic steps. Running a script is cheaper and more reliable than having the model regenerate the same code.
  • Show one good example of the output you expect.
  • Test the trigger. Try prompts that should use it and prompts that shouldn't.
  • Commit project skills to the repo so the team shares and versions them.
  • Only install skills you trust. They can ship executable scripts.
