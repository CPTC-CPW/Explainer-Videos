Meet the AP database

Every example here runs against AP, the accounts payable database you build in class with create_ap.sql. It tracks the bills a small company owes: who sent them, how much, and whether they've been paid.

Each table stores one kind of thing. Vendors are the companies that send bills, Invoices are the bills, and the other tables add detail. Tables point at each other through key columns: an invoice's VendorID says which vendor sent it.

This explainer stays inside one table at a time, mostly Invoices. Combining tables is the job of the joins explainer.

Key idea: a table is a grid. Each row is one thing (one invoice); each column is one fact about it (its total, its date). Queries pick rows and columns out of that grid.

A query asks a question

A SELECT statement is a question you ask the database: “which invoices haven't been paid yet?” SQL Server reads the table, works out the answer and hands it back as a result set.

The result set is itself a little table, with rows and columns. It only exists for that moment: SSMS shows it in the Results grid, and that's it.

Good to know: SELECT only reads. It never adds, changes or deletes data, so you can experiment freely. Run it a hundred times and the Invoices table still has 114 rows.

You write it in one order. SQL Server runs it in another.

A SELECT is built from clauses, each starting with a keyword. They must be written in a fixed order, and SELECT comes first, even though it isn't what happens first.

SQL Server first finds the table (FROM), then throws away rows that don't match (WHERE), then builds the columns you asked for (SELECT), and only then sorts what's left (ORDER BY).

Only SELECT and FROM are required. GROUP BY and HAVING belong to summary queries; we'll skip them here.

Key idea: keep the run order in your head: FROM → WHERE → SELECT → ORDER BY. It explains most of the “why doesn't this work?” moments in SQL. Each of the next chapters is one stop on that line.

FROM: start with the whole table

Everything starts with FROM. It names the table to read, and at this point every row is still in play: all 114 invoices.

The shortest useful query is SELECT * FROM Invoices. The * means “every column”, so you get all 10 columns of all 114 rows. It's handy for a quick look at a table you don't know yet.

Rows come back in no promised order. They often look sorted by the key, but SQL Server doesn't guarantee it unless you ask with ORDER BY.

Habit: use * to explore, then list the columns you actually need. Named columns are easier to read and keep working if someone adds a column to the table later.

WHERE: keep only the rows that match

WHERE runs second. It checks a condition against each row, one at a time. If the condition is true for that row, the row stays. If not, it's gone for the rest of the query.

Here the condition is InvoiceTotal > 1000. Of our 8 sample invoices, 4 pass. Across the whole table, 27 of 114 do.

The comparison operators are = <> < > <= >=. Text and dates go in single quotes: VendorState = 'CA', InvoiceDate >= '2023-01-01'. Numbers don't.

Key idea: WHERE decides which rows, never which columns. It can test any column in the table, even one you don't end up showing.

AND, OR, NOT — and why parentheses matter

Combine conditions with AND (both must be true) and OR (either one is enough). NOT flips a condition: NOT VendorState = 'CA' keeps everyone outside California.

The trap: SQL Server does AND before OR, the way math does × before +. Say you want invoices over 1000 from vendor 110 or 121. Written without parentheses, SQL Server reads it as (over 1000 from vendor 110) or (anything from vendor 121).

That version returns 13 rows, including six small invoices from vendor 121 that you didn't want. Adding parentheses around the OR gives the intended 7 rows.

Habit: whenever a WHERE mixes AND and OR, add parentheses, even if you think you don't need them. It costs nothing and makes your intent obvious.
Without parentheses · 13 rows
SELECT InvoiceID, VendorID, InvoiceTotal
FROM Invoices
WHERE InvoiceTotal > 1000 AND VendorID = 110 OR VendorID = 121;
With parentheses · 7 rows
WHERE InvoiceTotal > 1000 AND (VendorID = 110 OR VendorID = 121)

Shortcuts: BETWEEN, IN and LIKE

BETWEEN tests a range, and includes both ends. It's the same as >= the first value AND <= the second.

IN tests against a list. VendorState IN ('NV', 'AZ', 'TX') is a shorter way to write three = tests joined by OR.

LIKE matches text against a pattern. % stands for any number of characters (even none); _ stands for exactly one. So 'N_' means “N plus one more character”.

Mix and match: each one works with NOT too: NOT BETWEEN, NOT IN, NOT LIKE. And LIKE without a % or _ is just a slower =.

NULL means “unknown”, so test it with IS NULL

NULL isn't zero and isn't an empty string. It means no value is known. In AP, an invoice that hasn't been paid has no PaymentDate yet, so that column is NULL.

You might try PaymentDate = NULL. It runs without an error, but it returns 0 rows. Comparing anything to “unknown” gives “unknown”, never true, so no row passes.

The right tests are IS NULL and IS NOT NULL. They find the 11 unpaid and 103 paid invoices, which add up to all 114.

Key idea: never use = or <> with NULL. Always write IS NULL or IS NOT NULL.
FROM›WHERE›SELECT›ORDER BY
SELECT *
FROM Invoices
WHERE PaymentDate IS NULL;

SELECT: choose the columns

Only now, with the rows already filtered, does SQL Server look at the SELECT list. It decides which columns end up in the result, and in what order.

List the columns you want, separated by commas. Columns come back in the order you list them, not the order they sit in the table. Everything you leave out simply disappears from the result. The table itself is untouched.

Rows vs columns: WHERE trims the grid from top to bottom (rows). SELECT trims it from side to side (columns). They don't overlap.

SELECT InvoiceNumber, InvoiceDate, InvoiceTotal
FROM Invoices;

Calculated columns and aliases

A SELECT list can hold more than column names. It can hold expressions, worked out fresh for every row. Here, what's still owed on an invoice is its total minus what's been paid and credited.

The math operators are + - * / and % (remainder), with * and / before + and -, as usual. Use parentheses to change that.

A calculated column has no name of its own; SSMS shows (No column name). AS BalanceDue gives it one. That name is an alias: it only exists in the result.

Key idea: the new column is calculated, not stored. Nothing in the Invoices table changes. Run the query tomorrow after a payment, and the balance is recalculated.
FROM›WHERE›SELECT›ORDER BY
SELECT InvoiceNumber, InvoiceTotal, PaymentTotal, CreditTotal,
       InvoiceTotal - PaymentTotal - CreditTotal AS BalanceDue
FROM Invoices;

Gluing text together

In SQL Server, + between two pieces of text joins them into one string (this is called concatenation). Put a literal string in single quotes between them, like ' ', to add a space or other separator.

Vendors stores a contact's first and last names in separate columns. One expression and an alias turn them into a single readable ContactName column.

Watch out: if either side of a + is NULL, the whole result is NULL. Every AP vendor has both names, so it's not a problem here. When columns might be empty, CONCAT(VendorContactFName, ' ', VendorContactLName) treats NULL as empty text instead.
FROM›WHERE›SELECT›ORDER BY
SELECT VendorName,
       VendorContactFName + ' ' + VendorContactLName AS ContactName
FROM Vendors;

DISTINCT: each answer once

Ask for every vendor's state and you get 122 rows, one per vendor, with CA repeated 75 times. Usually the real question is which states do we have vendors in?

Put DISTINCT right after SELECT and duplicate rows are collapsed into one. The answer is 22 states.

DISTINCT looks at the whole row, not just the first column. SELECT DISTINCT VendorCity, VendorState returns 53 rows. The 41 vendors in Fresno, CA collapse into one row, but Washington DC, Washington IA and Washington NJ stay as three separate rows.

Order isn't promised: DISTINCT results often come back sorted, but that's a side effect. If you need them in order, add ORDER BY.

ORDER BY: sort what's left

ORDER BY runs last. By now the rows are filtered and the columns are built, so all that's left is to put them in order.

Sorting is ascending (ASC: A→Z, small→large, old→new) unless you add DESC. Here the 11 unpaid invoices come back biggest first, so the most urgent bills are at the top.

List more than one column to break ties: ORDER BY VendorState, VendorName sorts by state, then by name within each state. Each column gets its own ASC or DESC.

Key idea: without ORDER BY, SQL Server makes no promise about row order. If the order matters, say so.

Why ORDER BY can use an alias, but WHERE can't

Here's the run order paying off. The alias BalanceDue is created by SELECT, which is step 3.

ORDER BY is step 4, so the alias already exists and you can sort by it. WHERE is step 2: it runs before SELECT has named anything, so SQL Server has never heard of BalanceDue and stops with an error.

The fix is to repeat the expression in WHERE. The working query returns the same 11 invoices as the unpaid list: in AP, every invoice that still has a balance is one with no payment date.

Rule of thumb: a clause can only use names created by clauses that ran before it. When an error says Invalid column name and you're sure the name exists, check the run order.

Just the first few: TOP and OFFSET-FETCH

TOP 5, written right after SELECT, keeps only the first 5 rows of the result. Paired with ORDER BY, that answers questions like what are our five biggest invoices?

For the next five, use OFFSET and FETCH at the end of ORDER BY: skip 5 rows, then return 5. This is how apps show results one page at a time.

Vendor 110 owns four of the top five. That's the kind of thing a sorted, trimmed list makes obvious.

Always sort first: TOP without ORDER BY returns some 5 rows, not the biggest 5. OFFSET-FETCH won't run without ORDER BY at all.

FROM Invoices

Cheat sheet

Everything on one screen. If you remember one thing: write SELECT · FROM · WHERE · ORDER BY, but SQL Server runs FROM → WHERE → SELECT → ORDER BY.

SELECT [DISTINCT] [TOP n] column, expression AS alias, …   -- 3 · which columns
FROM table                                               -- 1 · which table
[WHERE condition]                                         -- 2 · which rows
[ORDER BY column [ASC|DESC], …                           -- 4 · what order
   [OFFSET n ROWS FETCH NEXT n ROWS ONLY]];
1 · FROM
  • Names the table; every row starts in play
  • * = every column; good for exploring
  • No promised row order
2 · WHERE
  • Keeps rows where the condition is true
  • AND before OR — use parentheses
  • BETWEEN (inclusive), IN, LIKE with % and _
  • IS NULL, never = NULL
3 · SELECT
  • Picks and orders the columns
  • Calculates new ones; name them with AS
  • + joins text; NULL + text = NULL
  • DISTINCT collapses duplicate rows
4 · ORDER BY
  • ASC by default; DESC for largest first
  • Several columns break ties
  • Can use SELECT's aliases (WHERE can't)
  • TOP and OFFSET-FETCH need it to make sense
