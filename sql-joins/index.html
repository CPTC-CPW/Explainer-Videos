The facts live in separate tables

The AP database keeps vendors in one table and invoices in another. An invoice doesn't repeat the vendor's name, address and phone number. It stores just one thing about the vendor: its ID.

That keeps every fact in one place. Federal Express has 47 invoices, but its address is stored once, in Vendors. Fix a typo there and every invoice sees the fix.

The catch: a question like “which vendor sent this invoice?” needs columns from both tables in one result. That's what a join is for.

Key idea: a join puts rows from two tables side by side, pairing up the rows whose key values match.

Keys connect the tables

A primary key identifies each row: no two vendors share a VendorID. A foreign key is a column that points at another table's primary key: Invoices.VendorID says which vendor sent the invoice.

This is a one-to-many relationship. One vendor can have zero, one or many invoices, but each invoice has exactly one vendor.

The AP script adds a foreign key constraint (FK_Invoices_Vendors), so SQL Server refuses an invoice whose VendorID isn't in Vendors.

Joins follow keys. Almost every join you write pairs a foreign key with the primary key it points at: ON v.VendorID = i.VendorID.

INNER JOIN keeps the pairs

For each vendor, SQL Server finds every invoice with the same VendorID and outputs one row per pair, with the vendor's columns and the invoice's columns side by side.

  • IBM appears twice, because it has two invoices. The vendor side repeats once per match.
  • Office Depot disappears. It has no invoices, so there's nothing to pair it with.
  • On the whole database this returns 114 rows, one per invoice, since every invoice has exactly one vendor.
Rule: an inner join only returns rows that found a partner on both sides. Anything unmatched is dropped silently.
SELECT v.VendorID, v.VendorName,
       i.InvoiceNumber, i.InvoiceTotal
FROM Vendors v
    JOIN Invoices i ON v.VendorID = i.VendorID
ORDER BY v.VendorID, i.InvoiceID;

Writing a join

A join goes in the FROM clause. Name the first table, then JOIN the second and say how rows pair up with ON.

JOIN and INNER JOIN mean exactly the same thing. Write INNER if it helps you read it.

Table aliases (v, i) are short names for the tables. Once a table has an alias, use the alias everywhere in that query.

Qualify shared column names. Both tables have a VendorID, so a bare VendorID is ambiguous and SQL Server stops with an error. Write v.VendorID or i.VendorID.
Anatomy
SELECT v.VendorName, i.InvoiceNumber, i.InvoiceTotal
FROM Vendors v
    INNER JOIN Invoices i
        ON v.VendorID = i.VendorID;
  • FROM Vendors v — the first, or left, table, with alias v
  • INNER JOIN Invoices i — the second, or right, table, with alias i
  • ON v.VendorID = i.VendorID — the join condition: which rows count as a pair
Forget to qualify a shared column
SELECT VendorID, VendorName, InvoiceNumber
FROM Vendors
    JOIN Invoices ON Vendors.VendorID = Invoices.VendorID;
Msg 209, Level 16, State 1, Line 1 Ambiguous column name 'VendorID'.

Chaining more tables

Each extra JOIN brings in one more table, paired on its own key. Here we follow one invoice all the way from the vendor to the general-ledger account each line item was charged to.

Invoice I77271-O01 from Wells Fargo Bank has four line items, so the result has four rows. The vendor and invoice columns repeat once per line item.

Run without the WHERE, it returns 118 rows, one for every line item in the database.

Read it as a path: Vendors → Invoices → InvoiceLineItems → GLAccounts. Each ON links the new table to one already in the query.
SELECT v.VendorName, i.InvoiceNumber,
       li.InvoiceLineItemAmount, g.AccountDescription
FROM Vendors v
    JOIN Invoices i ON v.VendorID = i.VendorID
    JOIN InvoiceLineItems li ON i.InvoiceID = li.InvoiceID
    JOIN GLAccounts g ON li.AccountNo = g.AccountNo
WHERE i.InvoiceID = 12
ORDER BY li.InvoiceSequence;

LEFT JOIN keeps every left row

An outer join also keeps rows that found no partner. A LEFT JOIN keeps every row from the left table, the one named first.

Office Depot has no invoices, but it stays in the result. SQL Server fills the invoice columns with NULL, meaning “no value here”.

On the whole database this returns 202 rows: the 114 matched pairs plus the 88 vendors with no invoices, one row each.

Use it when the question is about all of something: “list every vendor, with their invoices if they have any.”
SELECT v.VendorID, v.VendorName,
       i.InvoiceNumber, i.InvoiceTotal
FROM Vendors v
    LEFT JOIN Invoices i ON v.VendorID = i.VendorID
ORDER BY v.VendorID, i.InvoiceID;

Finding what's missing

The NULLs a left join adds are useful on their own. Keep only the rows where the right side is NULL, and you get the left rows that have no match at all.

That answers “which vendors have never sent us an invoice?” In AP it's 88 vendors.

Test the right table's key (i.InvoiceID). It can only be NULL when there was no match. A column like PaymentDate is also NULL on the 11 unpaid invoices, so testing it would mix two different questions.

Pattern: LEFT JOIN … WHERE right.Key IS NULL finds rows in one table with nothing in the other. Remember IS NULL, never = NULL.
SELECT v.VendorID, v.VendorName
FROM Vendors v
    LEFT JOIN Invoices i ON v.VendorID = i.VendorID
WHERE i.InvoiceID IS NULL
ORDER BY v.VendorID;

RIGHT JOIN is the mirror image

A RIGHT JOIN keeps every row from the right table, the one named second, and fills the left side with NULL where there's no match.

The ContactUpdates table lists new contact names for some vendors. Joining it to Vendors shows each update next to the contact on file. One update, for VendorID 28, matches no vendor, so its vendor columns are NULL.

Demo data: the VendorID 28 row isn't in the class AP script. We added it so this step has an unmatched row on the right; the original data can't produce one. To follow along, run ap-explainer-extras.sql on your AP database.

Most people rarely write RIGHT JOIN. Swap the two tables and use LEFT JOIN instead: same rows, and every query reads the same way — “keep everything from the table I named first.”

SELECT c.VendorID, c.LastName, v.VendorName
FROM Vendors v
    RIGHT JOIN ContactUpdates c ON v.VendorID = c.VendorID
ORDER BY c.VendorID;

FULL JOIN keeps both sides

A FULL OUTER JOIN (or just FULL JOIN) keeps every row from both tables. Matches pair up as usual; unmatched rows from either side get NULLs on the other.

It's the tool for comparing two lists: what's in both, what's only in the first, and what's only in the second.

On the whole database this returns 123 rows: 8 vendors with an update, 114 vendors without one, and the 1 update with no vendor.

Demo data: the unmatched right-hand row (VendorID 28) was added for this explainer by ap-explainer-extras.sql. Without it, every contact update matches a vendor.
SELECT v.VendorID, v.VendorName,
       c.VendorID AS UpdateID, c.LastName
FROM Vendors v
    FULL JOIN ContactUpdates c ON v.VendorID = c.VendorID;

CROSS JOIN: every combination

A CROSS JOIN has no ON. It pairs every row of the first table with every row of the second, so the row count multiplies.

3 vendors × 5 payment terms = 15 rows. Across all 122 vendors it's 122 × 5 = 610 rows.

That's useful when you really want every combination, like building a grid of vendors and terms to fill in or compare. It's rarely what you want by accident.

Watch the size: the result has rows in A × rows in B. Cross two tables of a few thousand rows each and you get millions.
SELECT v.VendorName, t.TermsDescription
FROM Vendors v
    CROSS JOIN Terms t
ORDER BY v.VendorID, t.TermsID;

A self join: one table, twice

Sometimes the rows you want to pair are in the same table. Which vendors are in the same city as another vendor? Join Vendors to itself.

The two copies need different aliases (v1, v2) so SQL Server knows which copy each column comes from.

Without v1.VendorID <> v2.VendorID, every vendor would also match itself, since it's in its own city.

Pairs go both ways: Compuserve–Micro Center and Micro Center–Compuserve are two rows. Across all vendors this returns 1,758 rows, because cities with many vendors pair each one with every other.
SELECT v1.VendorName, v1.VendorCity,
       v2.VendorName AS SameCityAs
FROM Vendors v1
    JOIN Vendors v2
        ON v1.VendorCity = v2.VendorCity
       AND v1.VendorState = v2.VendorState
       AND v1.VendorID <> v2.VendorID
ORDER BY v1.VendorCity, v1.VendorName;

ON or WHERE? It matters for outer joins

Goal: list every vendor, with any invoices over $1,500. Putting the invoice condition in WHERE looks natural, but WHERE runs after the join. Vendors with no big invoice have NULL there, NULL > 1500 isn't true, and those rows are thrown away. Your left join has quietly become an inner join.

Put the condition in ON instead. It then decides which invoices count as a match, and the left join still keeps every vendor.

Condition in WHERE · vendors lost 
SELECT v.VendorID, v.VendorName,
       i.InvoiceNumber, i.InvoiceTotal
FROM Vendors v
    LEFT JOIN Invoices i ON v.VendorID = i.VendorID
WHERE i.InvoiceTotal > 1500
ORDER BY v.VendorID;
Result · our 4 vendors2 rows · 24 on all of AP
VendorIDVendorNameInvoiceNumberInvoiceTotal
83Ingram313597831575.00
113Pollstar772901750.00

IBM and Office Depot are gone, even though this is a left join.

Condition in ON · every vendor kept 
SELECT v.VendorID, v.VendorName,
       i.InvoiceNumber, i.InvoiceTotal
FROM Vendors v
    LEFT JOIN Invoices i ON v.VendorID = i.VendorID
                      AND i.InvoiceTotal > 1500
ORDER BY v.VendorID;

IBM's invoices are all under $1,500, so it's kept with NULLs, just like Office Depot.

Rule of thumb: in a LEFT JOIN, conditions on the right table belong in ON. Conditions on the left table can go in WHERE. (For an inner join the two placements give the same rows.)

The old comma syntax

You'll see joins written the old way: list the tables with commas in FROM and put the join condition in WHERE. It returns the same 114 rows as an inner join.

The danger is forgetting the condition. Without it, the comma version is a cross join: every vendor paired with every invoice, 122 × 114 = 13,908 rows, and no error.

With JOIN, SQL Server won't let you forget: a JOIN with no ON is a syntax error.

Prefer explicit JOIN … ON. The pairing rule sits right next to the table it belongs to, filters stay in WHERE, and outer joins are only possible this way.
Old style · 114 rows
SELECT v.VendorName, i.InvoiceNumber
FROM Vendors v, Invoices i
WHERE v.VendorID = i.VendorID;
Old style, condition forgotten · 13,908 rows
SELECT v.VendorName, i.InvoiceNumber
FROM Vendors v, Invoices i;
